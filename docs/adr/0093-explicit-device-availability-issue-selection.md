# ADR 0093: Act on explicitly selected device availability issues

**Status:** Accepted; implemented, installed and verified for a local trial; unreleased
**Date:** 2026-10-17

**Later decision:** [ADR 0094](0094-one-device-issue-workflow.md) uses this selection contract for all current issues wholly owned by one registry device, with the same device entry from Open issues and Monitoring. It supersedes the availability-only membership and singular queue entry rules below. Exact episode links retain their original scope. The local trial receipt below records the earlier availability-only build.

**Partially supersedes:** The single-issue-only dashboard response presentation retained by ADRs 0064 and 0090. Extends the shared issue view in ADRs 0073 and 0091. Independent issue identity, recovery, history, notification instructions and exact operator effects remain unchanged. ADR 0074 continues to govern the separate availability-monitoring edit.

## Context

One device can have a device availability issue and separate availability issues for its media player, alarm and timer entities. Acknowledging only the device issue leaves the three entity issues unacknowledged, even when the owner is investigating them together. Repeating an entity's device-like friendly name also makes one device appear to be several. The owner approved an explicit collective selection in the shared dialog, with all shown issues initially selected and a single response area. Singular entry retains a direct response to its original issue without selection controls.

## Decision

Monitoring continues to explain source status and coverage. The device inspector orders device identity and availability first, monitored entity rows next, and monitoring coverage last. Its summary shows x of y monitored entities available, with one visible View button opening all current related availability issues in the shared dialog. Show View whenever any such issue is open, including when the aggregate device issue is absent or has cleared and only entity issues remain. The denominator is the device's monitored availability membership; the numerator uses the existing availability evidence classification. Missing or restored evidence retains its absent-evidence meaning. Entity counts remain separate from issue counts: the fixture has 0 of 3 monitored entities available and four open issues. Source inspectors do not duplicate acknowledgment or notification-pause controls. Closing the dialog restores the originating source or list context.

Each monitored entity has a compact row with its actual name linked to the Home Assistant entity and useful current status, wrapping on narrow screens. These rows have no separate View buttons or Homeostatic issue popups. Individual response exceptions belong to selection in the combined dialog. Omit repeated Unavailable labels only when the summary already conveys that uniform current state. Preserve concise row status for mixed availability and missing or restored evidence. Derive status from current evidence; absence of an issue does not establish availability.

The Monitoring device inspector and shared dialog each provide one clearly labelled Open device action. Do not also link the device name or repeat that destination within the same view. The dialog retains its own action because it can open directly from Open issues. Entity and integration destinations remain distinct. These presentation changes alter no policy, evidence rule or issue lifecycle.

A device availability entry opens the device's current aggregate availability issue, when present, and its independently open entity availability issues. When several issues are shown, select all initially. Use registry device membership, never matching names. Exclude unrelated condition types, other devices and wider integration issues. Preserve singular entry points from Open issues and deep links: they show only the original issue. Any view with only one current issue uses direct actions without a checkbox, selection count, repeated issue-name row or redundant Availability issue heading. Both contexts reuse the response workflow and exact action semantics with controls appropriate to the task. Neither entry point merges issues or changes their lifecycle.

Show one named device with an explicit Device label. Group child rows under Entities on this device. Show each entity's actual name once in the same style, including an entity whose name matches the device; the grouping establishes the relationship without special media-player labels or domain annotations. Distinguish the device availability assessment from each entity issue. Retain each issue's condition, acknowledgment and pause state.

When several issues are shown, place one All issues master checkbox above the issue rows, using normal body-size text with the selected count alongside. Give each issue row its own checkbox. The master selects or clears the currently shown actionable issues and reflects all, partial or zero selection. Provide one acknowledgment and notification-pause action area. The owner can uncheck exceptions or select one entity issue. Zero selected disables both actions. Preserve choices while selection remains applicable and after actions; newly arriving or replacement issues are not automatically selected. Ended issues cannot remain actionable or be replaced by a new identity in the selection.

Submitting acknowledgment or a pause captures the exact selected current issue IDs when selection is shown, or the displayed current issue ID in a one-issue view. The frontend invokes the existing per-issue services for those IDs and retains each result, including failures; this adds no backend batch contract or atomicity guarantee. Acknowledgment records awareness without clearing issues. A pause uses the chosen expiry for those issues only. Neither action establishes device-wide inheritance for future issues. Cancellation changes nothing; a refresh or a change between several and one issue must not change a pending submission's captured IDs.

Stop Monitoring remains a separate coverage change. Issue checkboxes do not determine its scope. Its own confirmation identifies the affected entities and availability policies; exclusions can end additional availability issues for those entities, while other condition checks continue.

## Acceptance

The [local trial receipt](../performance/device-availability-selection-2026-10-17.json) records the implementation checks, rendered review and installation separately. The frozen candidate passed bounded desktop-light and phone-dark workflows against isolated Home Assistant, plus browser history and direct-reload checks. These cover collective acknowledgment, individual pause exceptions, recovery to one remaining entity issue, guarded Stop Monitoring and preserved unrelated settings. The local installation passed startup and browser verification with matching component files and served frontend. The device inspector opened its four current issues with all selected and returned to its original source and focus. Saved settings and enabled notifications were unchanged. Physical Safari, live notification delivery and sustained household load remain outside this acceptance.

Use one device with an aggregate issue and three entity availability issues, including a media player whose name matches the device. Its Monitoring summary reads 0 of 3 monitored entities available, and its sole View button opens all four issues. Verify identity/availability, monitored entities and coverage appear in that order; entity names open Home Assistant without per-row issue buttons. Uniform unavailability needs no repeated row label; mixed and missing/restored evidence stays distinguishable, including without an open issue. Verify all four issues start selected below the All issues control and the master reflects all/subset/zero states. Clear or omit the aggregate device issue: View must still open remaining entity issues. With one issue left, provide direct actions without selection controls. Retain singular Open issues and deep-link routes. Check mixed acknowledgment/pause states, cancellation, partial failure, partial recovery, later arrivals and replacement identities during refresh and pending actions. Confirm other devices and condition types are untouched, and Stop Monitoring retains its independent confirmation scope. Inspect shared entry and return paths, one Open device action per relevant view, distinct entity/integration destinations, keyboard controls and desktop/phone layouts with isolated fixtures and mocked notifications. Configuration warnings require relevant configuration evidence; fixture content does not establish live installation state. Record the scoped executable and rendered acceptance separately from installation; prototype behavior alone does not establish either.
