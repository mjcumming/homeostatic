# Homeostatic integration specification

Date: 2026-09-27. Development baseline: Home Assistant 2026.9.3 and Python 3.14.

This is the integration implementation contract. [Homeostatic ADRs](adr/README.md) explain adapter decisions. The library design of record remains `health-tree/docs/rfp.md`; its accepted ADRs govern engine and policy behavior. This implementation includes situations, delivery and passive monitoring rules; the remaining release work is tracked in [roadmap.md](roadmap.md). HealthTree owns all attention decisions, including activation and reminder holds.

## Acknowledgment and early cancellation

Administrator actions `acknowledge(episode_id)` and `cancel_control(control_id)` use public HealthTree APIs under the runtime lock and save before confirming success. Operator actions first drain captured observations and evaluate due monitoring work against the current inventory. They rediscover sources only when inventory has changed or the engine needs initialization; an action alone does not force a full catalog scan. Periodic reconciliation remains unchanged. Acknowledgment uses the authenticated HA context user id; callers cannot supply an actor. The library owns the first time/actor, cross-recipient effect and restart persistence. An explicit rule option `require_acknowledgment: true` stops acknowledgment-dependent attention only. Recovery, dismissal, shelving and awareness remain distinct. Canceling a control ends only that request; overlapping maintenance and quiet hours remain effective. Missing, expired, removed or replaced control ids are rejected. A storage failure leaves monitoring unavailable and returns an ambiguous result that must be inspected before retrying.

The dashboard exposes these controls only when `inventory.attention_controls_supported` is true, displays acknowledgment from the read-only policy explanation, and disables actions when disconnected or for non-administrators. No notification consumer response is treated as acknowledgment implicitly. Built-in Companion delivery can provide an explicit phone Acknowledge action. The optional event-consumer blueprint does not provide that action; administrators can also acknowledge through the dashboard or native action.

The adapter uses public health-tree APIs for acknowledgment, cancellation and delivery grouping. The optional sibling-coalescing and split-event API is provided by the pinned health-tree dependency; see Development dependency. No alternate implementation or compatibility fallback changes those semantics.

## Ordered observation work slices

Queued observations retain their timestamps, ordering and atomic batch boundaries. The adapter yields to the HA loop after eight captured batches or 20 ms of elapsed processing, whichever comes first, while retaining its runtime lock. Elapsed processing uses a monotonic clock, independently of observation UTC timestamps. The budget is checked after each complete batch and its policy work; it cannot interrupt one synchronous engine call. New arrivals join the queue and are drained before current-state reconciliation, controls, persistence and publication. The current time is read after draining, preventing time from moving backward when new evidence arrives during a yield. No transition is dropped or collapsed by this scheduling change. Graph evaluation, reconciliation, serialization and catalog transfer still require measurement.

## Availability issue ownership

Homeostatic disables sibling coalescing with the public library setting `EngineSettings.coalesce_count=None`. A healthy shared integration does not merge independent availability checks, including failures discovered together after startup or later siblings. Confirmed failed-integration dependencies still suppress and absorb related failures. Recovery retains reconnect grace, then separates remaining failures. Device, entity and policy checks stay independent; notification collection retains each issue's identity and controls. A shared integration issue evaluates each affected monitored availability assignment independently. Integration Morning reporting cannot mask an affected entity's Immediate assignment. Compiler scopes include the selected check identity, so unrelated battery or condition findings do not inherit availability reporting. Public library predecessor records preserve pending deadlines and prior attention through absorption and splitting.

Older grouped issues transition through public split events. `EpisodeOpened.split_from` identifies the predecessor for inherited acknowledgment, pause and attention state; `EpisodeResolved` with `resolution: split` and `split_into` records the exact successor IDs without claiming recovery. The adapter retains these IDs in history and detected events, gives each inherited pause its own cancellable control ID, and withdraws obsolete notifications without an all-clear. Unknown evidence cannot clear previously known failures. Later unrelated failures inherit no controls. The library owns the transition and attention semantics; the adapter never rewrites its snapshots.

A check shared by several recovering integrations has one successor. An existing independent successor retains its controls. A new successor with multiple predecessors has no `split_from` and starts fresh attention; all predecessor histories link to it. This avoids arbitrarily inheriting suppression from one of several issues. Older adapter versions cannot read the new separation records; a rollback requires the matching saved-state backup and component/library versions.

Installation Settings exposes active timing controls only. Legacy saved `coalesce_count` and `coalesce_window` values remain accepted and round-trip for compatibility, but do not enable sibling grouping. The manifest, project dependency and lockfile use the published library API.

## Scope and setup

One Homeostatic config entry per installation. Fresh setup installs ordinary editable policies for integration, device and entity availability, Repairs and broken automations, enabled with supplied notification assignments. Battery and vacuum policies start disabled. Temperature, thermostat and UPS templates require configuration. Global notification sending starts off. The catalog uses HA config-entry state and entity availability evidence only. Registered entities use registry identity; state-only entities use the explicitly weaker `entity_id:` identity. Homeostatic's own entities and config entries are ineligible.

Disabled sources, including integrations and add-ons, remain accessible in Monitoring without availability issues solely due to disablement. Monitoring hides disabled sources by default in every grouping and search view. Show disabled sources reveals them; their details explain: "Monitoring paused while disabled. Saved monitoring choices resume when re-enabled." The toggle changes browsing only and preserves saved monitoring choices. Config entries with `disabled_by` set receive no availability checks from catalog rules or named policies. Disabling an enrolled entry removes its check through the engine's existing removal lifecycle; it does not produce passing evidence or claim recovery. Saved monitoring choices apply again on re-enablement. Related sources and Repairs retain their independent eligibility. Homeostatic has no separate Supervisor add-on inventory or runtime check; add-on-related HA sources follow their registry eligibility. A stopped add-on, disabled automatic startup, an unloaded integration or missing evidence does not establish disablement. Any future native add-on producer must use an explicit disablement signal.

### Conversion helpers and groups

`switch_as_x` (Change device type of a switch) config entries are ineligible. They wrap an existing switch to expose it as another entity type, so counting the helper entry as another monitored device duplicates the underlying capability. The converted light, fan, or other entity remains eligible for its own HA availability check, without a dependency on the omitted helper entry. This exclusion applies by source type, including installations whose saved policies match every integration; it is not a name-based display filter ([ADR 0001](adr/0001-omit-switch-conversion-helper-entries.md)).

`group` config entries and their group entities remain eligible because an owner can use a group as an aggregate control target in automations. The config-entry check can report whether HA loaded that helper, and the entity check can report whether HA currently exposes the aggregate entity. The Group row counts those HA sources, not the devices inside the group. It is not a physical device or a member-health rollup. In the pinned HA implementation, a light or binary-sensor group can remain available when at least one member is available, while another member is unavailable. Thus a passing group check never clears, replaces, or mutes an individual member's problem. Monitor the member entities separately when their operation matters. Homeostatic does not create dependency edges or infer device health from group membership. Keeping Group sources is a [proposed decision](adr/0002-retain-group-sources-as-limited-aggregate-evidence.md) pending review of their place and explanation in the list.

### Catalog selection

Named monitoring policies are the only equipment enrollment model. Policies compile their enabled selectors into internal catalog matching records and create independent condition identities. Catalog discovery is passive; disabled records remain browsable but ineligible for availability checks. Situations remain independent of equipment enrollment.

Selectors match registry identities and metadata. Fields are ANDed and values within a field are ORed. Supported metadata includes kind, domain, device class, entity category, integration entry and family, device, entity, area, floor and labels. Entity area overrides device area; floor follows the effective area. Labels combine entity, device and effective-area labels. Integration sources have no inferred location membership. Names never drive matching. Public policy fields and supported selector modes are described under Reusable monitoring and notification definitions.

An entity policy can additionally save `match_any` or `match_none`, mutually exclusive nonempty lists of entity-type clauses. Each clause requires `domain` and can narrow `device_class`. The base selector still applies; `match_any` requires one matching clause and `match_none` excludes every matching clause. General entity availability starts with the complement of cameras, locks, alarm panels and binary sensors of class smoke, carbon_monoxide, gas or moisture. Important equipment starts with that union. Both apply existing enabled operational eligibility, including standalone entities. These independent saved expressions track future entities and metadata changes; neither queries the other policy's current choices, existence or enabled state. General uses Morning and Important equipment uses Immediate, with identical evidence, severity and holds. Ordinary editing can create overlaps or gaps without a winner or fallback.

New matching sources enroll on registry changes, state appearance or the 15-minute sweep. Metadata changes re-evaluate policy scope. Integration lifecycle evidence arrives through each watched entry's state callback; an entry update that changes neither title, domain nor disabled state requests no refresh, while entry additions, removals, renames, disablement and other catalog changes still rediscover. Inventory includes the discovered candidates and contributing policies, including unmonitored candidates. It retains at most 50 activity records for the current runtime: an initial scope snapshot, followed by changes grouped by reconciliation id. Activity is not persisted across reloads. There is no separate saved catalog-rule editor, inheritance hierarchy or rule-preview service.

Ordinary temperature readings and thermostat target or action changes enter the ordered observation queue without invalidating the catalog. A selected thermostat changing between supported and unsupported operating modes still reconciles its checks. Missing, restored, unknown and unavailable evidence retains the existing enrollment rules. Unselected climate updates do not trigger discovery solely because a thermostat policy exists; relevant metadata changes and periodic reconciliation still apply.

Monitoring summaries distinguish integration instances, device summaries, entities with devices and entities without devices. These are inventory groupings, not inferred physical or software classifications.

### Monitoring policy presentation

Home Assistant creates the integration entry in one step. It exposes no Configure flow or integration YAML fields. Policies is the monitoring editor for fresh setup. Supplied and user-created policies appear in one list with the same edit, duplicate, enable, disable and delete actions. Edit stays visible in each row; Enabled belongs to the policy draft. A labelled More actions button opens Duplicate and Delete in a compact popup sized to its contents and bounded by the viewport. It supports keyboard access and closes with Escape or an outside click. Opening or dismissing it changes no draft settings. Each row shows its saved On or Off state beside the name, or Not saved for a new policy. A pending enable or disable says it will take effect when saved; reversing that change removes the pending message. Editing again clears the previous save confirmation. Monitoring shows applicable policies and links to their editors. Notifications manages reusable delivery methods and activation. Each saved method has its own explicit Send test action.

Choose Monitoring type when adding a policy. The saved type is immutable; use a new policy for a different type. A duplicate keeps the type, receives its own identity and starts disabled. Source selectors and detection fields depend on the selected type's actual capabilities. Policies select reusable named notifications; Notifications owns their timing and selected delivery methods.

Rendering changes no configuration. Navigation retains the complete pending draft. Each configuration editor uses its scoped save action without a separate Review button, review screen or preview prerequisite. Save validates the exact submitted draft, checks the saved revision, serializes changes and rolls back options if applying them fails. Existing internal preview/token checks may run within that action; public read-only preview APIs remain available. Validation and save failures explain the problem and preserve the draft. This applies to Policies, Notifications and Settings. Selective restoration adds explicitly chosen missing supplied policies to the draft without overwriting surviving policies; Save applies it. Reloads and updates preserve edits and deletions. The detailed model and first-run choices are specified below.

### Home Assistant device availability

Device details retain the availability vocabulary adopted in [ADR 0035](adr/0035-align-device-availability-with-ha-proposal.md): Available, Partially available, Unavailable, Unknown, and Disabled. [ADR 0064](adr/0064-monitoring-coverage-and-device-evidence.md) defines the entity fallback over enabled operational registry entities, including buttons and hidden entities, while excluding diagnostic and configuration entities. Disabled devices take precedence. Any current non-unavailable state, including unknown or a connectivity sensor's off value, establishes Available. Every eligible entity currently unavailable establishes Unavailable. An empty set, no current states, or unavailable states mixed with missing/restored evidence establishes Unknown. Restored values do not establish current availability. This read-only assessment does not create monitoring checks. Native integration reports retain their separate precedence when the upstream API becomes available.

The pure report reducer gives attached, loaded integration reports precedence: matching reports establish Available or Unavailable, and mixed reports establish Partially available. Only actual reports participate; absent reports are not negative reports. It retains provenance and consumes a current snapshot, so unloaded or detached entries cannot contribute. The supported HA version has no report API, so production uses entity fallback and never manufactures Partially available from mixed entity states. Native integration-report ingestion remains pending upstream.

The `homeostatic/source` and `homeostatic/node` replies carry `device_availability` with status, basis, reason, entity ids/counts, current connectivity ids, and integration reports. Non-device replies carry null. Disabled and empty registry devices remain browsable without acquiring monitoring checks. The Monitoring device view and issue detail display availability separately from selected-entity findings. The selected Monitoring view refreshes when HA access or connectivity evidence changes, including unmonitored members; other ordinary value changes do not refresh availability. This assessment itself creates no episodes, dependency edges, notification requests, or saved settings. The selected-entity monitoring contract below remains separate.

[ADR 0012](adr/0012-monitoring-expectations-and-persistent-exclusions.md) defines availability expectations. [ADR 0025](adr/0025-follow-home-assistant-availability-semantics.md) supersedes its member eligibility and status mapping: an HA `unknown` value is not an availability fault. [ADR 0045](adr/0045-device-issue-requires-every-selected-entity-unavailable.md) limits the device warning to total unavailability.

Selecting an entity's availability check declares that it is expected to be available. Selecting a device summary extends that expectation to its eligible members. Discovery alone makes no such declaration. Fresh setup enables separate supplied integration, device and entity availability policies with notifications off. Broad, area and label entity availability selections cover enabled operational entities, including entities without devices; diagnostic and configuration categories are excluded. An exact entity selection opts that entity into availability monitoring, including diagnostic or configuration entities, while disabled sources remain ineligible. This eligibility applies to saved policies without resetting their selections. Battery, UPS and temperature condition checks retain their configured diagnostic inputs.

Each device summary uses enabled operational entities, including buttons and hidden entities. Diagnostic and configuration entities never supply its availability evidence, even when no operational entities exist. A button's unknown last-pressed value is available evidence. Disabled entities, devices and integration entries are excluded using their registry disabled_by fields, never by interpreting unavailable, missing, unloaded or stopped states as disablement. Disabled sources remain browsable without checks; removing their checks ends monitoring without asserting recovery. Saved choices resume on re-enablement. A device with no eligible members has no availability check. Each device policy applies its own entity-member exclusions; a separately configured entity policy does not change those members. No brand, entity-name, or unique-id-suffix exception determines health.

For passive availability, an HA `unknown` state means its value is unknown while HA still supplies a current state. Current `off` and `idle` states also establish availability, including `off` from a connectivity-class binary sensor. A device summary warns only when every selected member is `unavailable` (`all_unavailable`). One selected member with a current state makes the summary pass even when others are unavailable. When no selected member has a current state and some evidence is missing or restored, the summary is unknown (`incomplete_evidence`). Missing or restored evidence cannot establish recovery and follows the existing unknown-evidence hold. These observations do not prove physical freshness or a physical failure. A watched device depends on its watched associated integration entries for issue grouping without changing the device's own observation. [ADR 0064](adr/0064-monitoring-coverage-and-device-evidence.md) supersedes the diagnostic fallback and connectivity-off monitoring warning.

The device monitoring summary describes availability through Home Assistant across its policy's eligible members. It is an adapter-owned check, not a device-registry state or an overall equipment-health verdict. The separate Monitoring assessment uses enabled operational entities and the same HA availability semantics. Its inventory scope can differ from a policy's exclusions; the selected evidence and counts reflect the actual policy check rather than silently including excluded members. Episode activation and recovery retain the library holds.

| Selected entity evidence | Summary meaning | Observation |
| --- | --- | --- |
| At least one member has a current state, including `unknown`, `off` or `idle` | Reachable through Home Assistant | `pass/available` |
| Every member is unavailable | All monitored entities unavailable | `warn/all_unavailable` |
| No member has a current state, and not every member is unavailable | Insufficient current evidence | `unknown/incomplete_evidence` |

A passing summary does not prove that every member is available: some may be unavailable, missing or restored. Their states stay visible in device details, and their independent entity findings remain actionable. A passing sibling or device summary cannot clear an entity issue. An empty selected set attaches no check; an unmonitored or disabled device is not assessed as available. These distinctions do not add library statuses or change HA entity states.

Monitoring changes belong to the contributing policy. Narrowing its scope, disabling it or deleting it removes that policy's check without changing other policies. Removal ends an open issue without claiming recovery. Acknowledgment means awareness; temporary shelving means postponing attention; neither changes monitoring expectations.

An entity without an HA device remains an independent candidate. A device source uses its stable registry id and has no edge to its selected member entities. Its edges to watched integration entries group simultaneous control-path failures. Device issue cards lead with the affected entity and observed availability condition; they omit a generic availability label. Device problem details lead with the HA device name, the reported condition and other affected selected entities, then the device-page action. The integration type is quiet context shown once. Entity labels may omit a repeated device-name prefix when the remainder identifies the entity; a name identical to the device retains its full name. Affected entity names and conditions appear directly, including a single affected entity. When selected-entity findings and the operational device assessment conflict, a concise explanation identifies the different scopes. Working entities and check totals stay out of the problem brief. Acknowledge issue and Pause notifications precede optional monitoring choices. Opened issues show relevant additional readings, check contributions and technical evidence directly. Device inspectors show the monitored availability count and entity names directly, followed by monitoring coverage. They omit the Details disclosure and keep one View for all current issues wholly owned by that device. Large lists remain bounded and completely reachable; contributing policies can be opened for editing. This on-demand list is current evidence, not historical proof of the episode's cause.

The runtime indexes each eligible entity to every independent device-policy check that uses it. It captures queued member state changes against that check's own member set, so an entity excluded from one policy can still affect another. Repeated changes leaving a check's availability condition unchanged do not create redundant observations. Registry changes and periodic reconciliation rebuild membership. A device loses its availability check when no eligible members remain, including after exclusions, while its saved selections and browsable identity remain available for later eligible evidence. Notifications retain their separate activation setting.

### Live dashboard

Frontend updates version the panel and generated-card element names as well as their module URLs. Loading a new module in a retained Home Assistant session must register a new current element instead of selecting an older constructor already held by the browser. Previously configured card names remain accepted.

The integration registers a Homeostatic sidebar dashboard at `/homeostatic`, a reusable `custom:homeostatic-card`, and a `custom:homeostatic` dashboard strategy. The strategy creates Open issues, Monitoring, Policies, Notifications and History views. Open issues is the default destination. History is a separate top-level page, and Settings is a header utility. Existing Overview and functions links open Open issues; other older card view names remain accepted. Existing user dashboards are not rewritten. Meaningful destinations have routes, including issue details, selected sources, policy editors and method editors. Browser Back and Forward restore search, grouping, expansion, selection and scroll without discarding drafts. Drafts and pending saves also survive replacement of the panel when the same administrator leaves Homeostatic and returns in the same tab. This in-memory session ends on reload, tab closure or an authentication change; saving is never retried merely because a panel is replaced. Contextual return controls lead back to the originating view. Each screen presents its task and each return route once. The primary Policies and Notifications buttons open their lists while retaining pending drafts. Monitoring returns to its tree on narrow screens and retains the selected source and filters. Contextual Back restores the originating object; source details keep a separate Back to Monitoring action when the origin is an issue. Lists show the name, useful state and one way to open the item; full findings, usage lists and technical explanations belong in details. Optional filters and advanced installation timings start collapsed, with active filters identified in their summary. Timing shows setup retries, recovery confirmation and the startup wait first; other installation waits remain under Advanced timing. Loading states offer retry only after a failure.

Every active Home Assistant Repair, except those Homeostatic raises, is a `repair` source with its own episode. Its name is the Repair's translated title, its finding names the raising integration and severity, and its link is the automation editor when the Repair carries one and the Repairs page otherwise. The episode ends when Home Assistant deletes the Repair or the owner ignores it. During the startup hold, a stored Repair that its integration hasn't raised again keeps its episode open. In the unified model, each Repairs policy owns its notification assignments; the supplied policy selects Morning summary. Up to 500 Repairs are tracked. Trace-only run errors stay outside this contract ([ADR 0044](adr/0044-report-home-assistant-repairs-as-issues.md)).

Each loaded automation that names an entity id present in neither the entity registry nor the state machine is one `broken_automation` source. The issue uses the automation's name, lists the missing ids, and links to that automation in the editor. The check runs after startup, when automations reload, when an entity registry removal or an id change asks which automations still name that id, and when a created entity id is named by an open issue. Other registry updates do not run it. If the automation component is not loaded, the check does nothing and does not end issues it already opened. The issue ends when the automation no longer names a missing id, the automation is gone, or the entity exists again. It is outside the dependency map and does not change enrollment or edit the automation. In the unified model, enabled Broken automations policies select this check and own their notification entries; the supplied policy selects Morning summary. Turning Repairs off leaves this check on. Unavailable, unknown, and disabled entities do not open it. Template-only ids, device triggers that never resolved to an entity id, and scripts stay out ([ADR 0050](adr/0050-flag-automations-that-name-missing-entities.md)).

History and source browsing are read-only; issue details expose explicitly requested operator actions. Open issues, Monitoring, Policies and Settings provide guarded monitoring, timing and notification edits in the panel. Stop Monitoring is available inside an opened current issue, with exact scope and confirmation as described under Presentation and queries. Closing that issue discards an unsaved review. Saving commits policy exclusions without a saved-action Undo; later changes use the applicable policy settings. All dashboard WebSocket commands enforce administrator access. The integration exposes no native Configure form.

Without `compact: true` or `paged: true`, `homeostatic/subscribe` sends a schema-version-1 snapshot after subscription acknowledgement and on runtime publication. It contains availability, current equipment readiness, inventory, active episodes, operator controls, coverage, policy explanations, and HA location names. It never reads engine snapshot internals or advances time. Startup, storage error and unload publish `available: false`. Subscriptions survive entry reload and end on client unsubscribe or disconnect.

`homeostatic/node` accepts one `node_id` and returns its source, public explanation, potential impact and readiness (null for situations). Unknown nodes return `not_found`; unavailable monitoring returns `not_ready`. Subscription, node detail, configuration read and previews do not mutate state. `homeostatic/save_settings` validates and saves the current policy configuration; scoped frontend drafts submit only their intended changes over the saved configuration. Enabling requests can authorize messages for already-open episodes after reload. Read endpoints do not perform operator actions or request notifications; operator services and explicit saved-method tests retain their separate contracts.

### Monitoring workspace target

Monitoring combines the former source browsing and monitoring views under [ADR 0017](adr/0017-one-sources-workspace.md). Grouping changes presentation only; they do not change enrollment or notification state.

The primary navigation is **Open issues, Monitoring, Policies, Notifications, History**, with Open issues as the opening page. Monitoring retains the existing `/sources` routes and source identities. Its heading explains the inventory as devices, entities and integrations; Policies uses the fuller page heading Monitoring policies. Issue history is available on its own top-level page; installation Settings remains a labeled utility. Monitoring combines discovery, current evidence, contributing policies, and retained source history in one canonical detail panel without mandatory subtabs. Navigation retains source selection and scoped drafts, and browser Back returns to the previous context. Policies owns monitoring scope, problem criteria and notification assignments. Notifications manages reusable named notifications and delivery methods. The persistent global notification switch remains independent of editor drafts. ADRs 0061 and 0070 record the navigation decisions.

Monitoring provides **By integration**, **By Home Assistant location**, and, when its read-only tree is available, **By Topomation** views. Integration is the initial default; remember the owner's grouping thereafter. Home Assistant location uses HA floors and areas. A floor lists its areas. Devices and entities appear under the area they belong to. A grouping switch preserves the selected source by stable identity and reveals its new path. Unlocated sources, floorless areas, entities without devices, and sources without a known integration remain explicitly reachable. Integration entries and other non-location sources have a suitable Other sources fallback rather than a fabricated area or device. Location grouping creates no dependency. The watched device-to-integration edge follows the HA entry association described above.

When Topomation's read-only `topomation/locations/list` response supplies a usable tree, the Group by menu offers Topomation explicitly. That view uses its ordered parent-child hierarchy, explicit entity placements and HA area mappings. Unplaced sources remain under Unassigned. Home Assistant location always uses HA floors and areas. If Topomation becomes unavailable while selected, return to Home Assistant location. This changes presentation only; it never changes monitoring, dependency, readiness or attention decisions ([ADR 0024](adr/0024-explicit-topomation-grouping.md)).

Monitoring describes the optional TopoMation hierarchy beside Group by and links to its integration page whether or not the tree is available. When available, the note identifies the TopoMation choice and whether it is selected. The link is informational and does not install or configure another integration.

The Monitoring toolbar places Search first, followed by Monitoring status and a More filters button. Search covers the complete inventory. Monitoring status offers All, Monitored and Not monitored, with All selected initially. More filters opens an anchored panel without resizing or rearranging the toolbar; active filter state stays visible, Escape closes the panel and restores focus, and live updates preserve its fields and open state. Group by and a stable Collapse groups button sit immediately above the tree. Collapse groups changes only tree expansion, leaving filters, selection and source details intact. It intersects with search and existing filters, retains matching sources' ancestors, and never changes saved monitoring. Coverage comes from actual active checks, including device availability contributions and named temperature, battery or UPS evidence inputs; shared device membership alone creates no coverage. Disabled sources retain their separate browsing option. Returning from another page preserves this filter. A selected source stays inspectable after a filter or saved monitoring change removes its row from the results. **Needs review** is a filter with issue indicators, not a flat preamble of repeated findings. Initially render compact collapsed groups; gaps alone do not expand them. A source link or search reveals only the necessary ancestor path. The disclosure control changes expansion independently of selecting the row. Tree rows use neutral text and a transparent background, with consistent indentation for each child level. Open issue indicators use labeled warning-tinted surfaces with neutral text. Primary navigation combines a theme-accent indicator and selected surface with its accessible current-page state; color never replaces labels. Hover applies to the whole row; only the selected source or its paired device row receives a primary-color tint. With no valid selection, no row is highlighted. Keyboard focus remains visibly distinct from selection. Live evidence updates retain selection, expansion, search focus, and reading position. Large branches render on demand with a bounded visible working set, using windowing if necessary; do not reintroduce nested pagination, a separately scrolling tree window, or new grouping levels just to divide a long integration list. ### Battery maintenance producer

Homeostatic discovers battery percentage (`sensor` or `number` with battery device
class), explicit low-battery (`binary_sensor` with battery device class), and
charging (`binary_sensor` with battery-charging device class) from HA metadata.
Charging alone is context, not a monitored battery. Battery candidates appear in
Monitoring and remain unmonitored until a saved catalog rule selects their
`battery` check. Each rule selects one check: `availability`, `battery`, or
`vacuum`. A rule enrolls only the check it names. The battery candidate is an
edgeless maintenance node, separate from HA availability.

One percentage and one explicit warning on the same HA device are offered as one
reviewable battery candidate. When several percentage or warning entities belong
to one device, each is offered separately; charging is associated automatically
only when there is one battery candidate and one charging entity. An entity
without an HA device remains its own candidate. The source uses its primary
entity's registry identity where available. A changed source grouping retires
the old monitoring identity as removed, never as physical recovery. Source details
show all paired entity ids so an owner can leave a mistaken pairing unmonitored.

A current percentage at or below the policy threshold (20% by default) or an explicit low warning is `warn` /
`battery_low`; contradictory low and normal reports remain a warning with a
conflict marker. A current, confirmed charging report for that battery is
`pass` / `charging` even while a low report remains. A current percentage above
the policy threshold and an explicit normal warning clear the low condition when all configured
low signals are current and normal. Missing, unavailable, invalid, or restored
low evidence is `unknown` unless another current signal reports low or charging
is confirmed. Missing charging evidence cannot itself clear a low condition.
If charging stops while low evidence remains, the warning can open again. Battery
checks have zero raise and clear hold and no physical-freshness TTL; HA state
updates do not establish a device-originated heartbeat. A charging clearance
means this monitored condition ended, not that the battery was replaced or is
fully charged. Current readings, entity ids and conflicts remain available as
evidence; replacement type remains unknown without verified metadata. Existing
reporting preferences and attention rules govern delivery.

### UPS condition producer

Homeostatic maps NUT and APC UPS Daemon entities into one UPS producer. Discovery uses the integration's full entity unique ids and the device identifier's integration and id, including separate devices on one server. Further identifier fields are ignored. A candidate requires mapped raw status and battery charge or remaining runtime. Entity names never identify roles. Disabled diagnostics remain disabled and are shown as optional missing evidence. Conditions begin unmonitored until a named policy selects them.

Each UPS condition is an independent edgeless node: `ups_power`, `ups_reserve`, `ups_battery_replacement`, or `ups_fault`. Named policies create stable device/condition identities qualified by policy identity and detection settings. Backup operation warns, replacement warns, and explicit faults fail; NUT bypass warns about lost protection. Mains input alone cannot prove output to connected equipment. No power wiring or equipment dependency is inferred.

NUT reads raw `ups.status` flags. `OB` and `OL` establish backup and mains mode; `LB` and `RB` report reserve and replacement warnings. `OVER`, `OFF`, `FSD`, and `ALARM` report faults; `BYPASS` reports lost protection. `TRIM` and `BOOST` alone pass the fault check, and calibration/test flags remain context. APC UPS Daemon maps `ONLINE`, `ONBATT`, `LOWBATT`, `REPLACEBATT`, `OVERLOAD` and `NOBATT`. Its `COMMLOST` report invalidates cached condition measurements rather than asserting a hardware failure. Unrecognized flags are retained in technical evidence.

Reserve can supplement an explicit warning with owner-selected charge or runtime threshold pairs. Values at or below the low threshold warn. Once low, values must reach the higher recovery threshold to clear. Without a custom pair, a readable mapped device low setpoint is used, and recovery requires a value above it. Runtime is normalized from its reported seconds, minutes or hours into minutes. Explicit warnings cannot be canceled by a conflicting numeric value. All enrolled reserve signals must be current and normal for recovery. Charging alone clears none of the UPS conditions. Checks have zero raise hold, the configured clear hold, no physical-freshness TTL, and the existing unknown hold.

Missing, unavailable, restored, disabled, invalid or contradictory mode evidence never clears a condition. Retain enrolled signal bindings while their HA device and owning entry exist, including through restart; registry removal of a signal and an orphaned state under its former name are unknown evidence. Explicit device or entry removal ends monitoring as removed. Persist last confirmed power mode, numeric hysteresis and device thresholds independently of the opaque engine snapshot.

Reserve notification rows explicitly select `when: mains` or `when: backup`. A new reserve template selects Morning summary for mains and Immediate with acknowledgment for backup when those definitions exist; existing assignments remain unchanged. Before any confirmed mode, reserve is dashboard-only with a visible evidence gap. Missing mode evidence retains the last confirmed reporting mode while low reserve is established. A confirmed transition into backup mode rearms an earlier acknowledgment through the public `Policy.rearm` API, preserving the issue and its shelf. Returning to mains disables backup-route reminders and leaves the reserve issue open until its own recovery.

UPS reserve and generic battery monitoring may overlap independently without ownership transfer. Each policy keeps its findings and notification assignments. Disabling or deleting one does not rewrite the other policy.

The Open issues page groups conditions under one UPS, with current issues sorted newest first by default. One View opens its device dialog; explicit selection applies acknowledgment or pause to the chosen independent issues. Counts represent conditions consistently across pages. Monitoring lists applicable policies; Policies owns thresholds and condition-specific notification rows, and Notifications owns the reusable timing and delivery definitions. The compact card shows useful readings with runtime labeled as an estimate. Issue details lead with the reported condition and next step, with relevant reported flags visible as supporting evidence. Partial recovery keeps the remaining conditions visible.

### Vacuum error producer

Homeostatic offers every `vacuum` entity as its own candidate
([ADR 0046](adr/0046-report-vacuum-error-activity.md)). Candidates stay
unmonitored until a saved catalog rule selects the `vacuum` check. An
availability rule leaves that check off, and a vacuum rule leaves availability
off. A broad vacuum policy may cover current and future vacuums.

The check reads the entity's current activity. `cleaning`, `docked`, `idle`,
`paused`, and `returning` pass. `error` fails with reason `vacuum_error`.
`unavailable`, `unknown`, a missing state, a restored state, and any other
value are `unknown`. Unknown keeps an open issue open. The check has no raise
hold and no clear hold. The finding says Home Assistant reports the vacuum in
error. When Home Assistant has an area for that vacuum, the notification names
it. That area is the device's assignment in Home Assistant.

The source is its own node and has no dependency edges, so a failed integration
does not absorb it. Availability of the same entity, when watched, stays a
separate issue. A change from one ordinary activity to another, including
`cleaning` to `error`, is observed even though both are available states.

On a generated reporting policy, a vacuum error uses Immediate unless that
vacuum has its own source preference. The fallback matches check `vacuum` and
sits immediately ahead of the empty household rule, so a source preference
still wins. Immediate sends once, including overnight. When Immediate has no
recipients, the issue is recorded in the panel. Custom policies are left as
written. Discovering a vacuum sends nothing. Homeostatic does not command the
vacuum.

### Configured temperature producers

Each selected source and named policy has an independent temperature monitor. Temperature limits require a finite minimum, maximum or both, an explicit duration from zero to 365 days, and °C, °F or K. Minimum cannot exceed maximum. Policy list summaries omit an unset minimum or maximum, including a saved null value, retain zero and negative limits, and express durations in whole hours or minutes when exact. The temperature editor shows equally weighted optional Below and Above fields and requires at least one. Duration starts in minutes for whole-minute values, including zero, with hours available; existing partial-minute values start in seconds. Display-unit changes preserve canonical integer seconds and do not dirty the draft. Invalid bounds or durations retain the draft with a nearby explanation before saving. A live rule summary describes qualification separately from notification timing. Policy enabled appears beside the editor heading and applies with Save policy. A saved global notifications-off state is explained beside the notification assignments. Source selection preserves picker scroll, search and focus through selection and live updates. Thermostat defaults are a 2 °F permitted margin, 2 °F meaningful progress, 2 °F worsening and a one-hour progress interval; the interval must be positive. Policy copies have independent identities. Detection edits retire the affected check and its pending qualification before starting the replacement; renaming leaves monitoring untouched.

The sensor producer reads the current state and its `unit_of_measurement`. The thermostat producer reads `current_temperature`, `temperature`, or the `target_temp_low` and `target_temp_high` pair. In the supported HA 2026.9 Core, climate attributes are converted into the installation temperature unit; the caller supplies `hass.config.units.temperature_unit`. The producer does not infer units from the thermostat hardware. These contracts follow the [sensor documentation](https://developers.home-assistant.io/docs/core/entity/sensor/) and [the supported climate implementation](https://github.com/home-assistant/core/blob/2026.9.3/homeassistant/components/climate/__init__.py).

Normalize absolute readings and targets into Celsius and round comparisons to six decimal places. Difference conversion applies the scale only, with no absolute-temperature offset. Equivalent normalized targets do not reset progress. The check observes reported values; repeating a cached value at a deadline does not establish physical freshness. No sensor placement, equipment defect or physical freeze prediction is inferred.

A temperature-limit reading outside either bound starts continuous qualification. Equality is in range. At the duration deadline, an ongoing violation warns; duration zero warns immediately. An in-range reading cancels qualification or clears the condition. A direct low-to-high or high-to-low jump without an observed in-range reading preserves qualification and issue identity, while updating the violated bound. There is no additional recovery threshold.

Thermostat `heat` checks below target minus margin; `cool` checks above target plus margin; `heat_cool` uses its low and high targets respectively. Equality is permitted. HVAC action is context and never a prerequisite or reset trigger. A new target, mode or conditioning direction starts a new comparison context without crediting the smaller target gap as measured progress. Off and unsupported modes return a removal instruction: retire the check as monitoring ended, without issuing a passing observation. Missing or unavailable modes are unknown evidence instead.

Within an unchanged thermostat context, retain the best temperature reached, a last-credited comparison temperature and its time. Improving the best temperature by the configured progress amount credits one new interval from that observation. Smaller steps accumulate; returning to an already reached temperature earns no credit. A fall away from the best temperature by the configured worsening threshold warns immediately. Cooling reverses these comparisons. This best-temperature baseline allows deterioration after useful recovery to qualify. Missing the progress deadline warns as stalled. A usable observation at exact deadline equality is evaluated for recovery and meaningful progress before stall; progress first observed after an elapsed deadline cannot erase the stall. Timers revisit current evidence at the returned deadline.

Once qualified, thermostat progress alone does not clear an issue; entering the margin does. A later worsening observation updates the same issue. A changed target that already satisfies the margin clears with a target-satisfied reason, distinguishing the changed expectation from measured improvement. An open issue remains open when the new target still lies outside the margin.

Missing, unknown, unavailable, restored, nonnumeric, nonfinite, unsupported-unit and malformed target-range evidence emits unknown and discards pending qualification and progress history. It never clears a qualified finding. Current usable evidence starts a fresh observation interval; an already-qualified condition remains qualified until its own recovery evidence or monitoring removal. Persistence retains only the qualified reason. Restart discards pending intervals and temperature comparisons so unobserved downtime cannot qualify a new issue or manufacture progress. The adapter restores the library's issue independently and supplies fresh producer observations. Producer observations have no freshness timeout; check enrollment owns the existing unknown-evidence hold. Availability monitoring remains independent.

Producer evidence includes source identity, normalized temperature, configured bounds or targets, thresholds, current observed interval and an explicit unverified physical-freshness flag. The temperature timeline fixture covers duration equality, gaps, restart, conversion, oscillation, changed targets and progress. Monitoring and reporting configuration use the validated single-save path; these producers do not request delivery directly.

## Time and lifecycle

Create or restore the engine only after HA has started. Load listeners and entities earlier, reporting unavailable until startup completes. One adapter owns calls into engine and policy on the HA event loop. Observations arriving together are ingested atomically. State and entry callbacks capture observations with their receipt time before queuing work. Every captured transition is applied in order, even if storage is busy. Each transition is its own observation batch; reconciliation must not erase it. Registry changes trigger an inventory refresh; a sweep every 15 minutes catches missed lifecycle changes, pending reauthentication and metadata retained for vanished sources, while the deadline timer covers the startup grace, the longest startup wait and each retry hold, re-observing an entry whose retry hold elapsed ([ADR 0098](adr/0098-update-the-subject-and-sweep-rarely.md)). A deadline timer uses the earlier engine/policy deadline, independently of reconciliation. No delay is added to batch unrelated observations. One queued refresh worker drains captured transitions in receipt order; redundant wakeups share that worker. New observations during persistence request another pass. A failed pass is retried by subsequent evidence or reconciliation, without a busy retry loop. Shutdown drains captured evidence under the same serialization lock and cannot rearm work.

Availability-only events use an entity-to-source index and the existing catalog. Entity registry changes, config-entry additions/removals, state arrival/removal, source-name/device-class changes and the explicit or 15-minute sweep rediscover inventory; a monitoring edit that changes only rules or exclusions re-evaluates the last registry scan without reading the registries again when no such change happened since that scan and keeps the decisions of candidates the edit does not name, while an edit that selects different sources scans again and the next reconciliation refreshes metadata retained for sources that have since disappeared; periodic reconciliation still captures missed config-entry and reauthentication changes. An observation callback does not rebuild unchanged inventory or reread every entity. Deadlines reobserve enrolled integration conditions to preserve retry escalation, and advance engine/policy timing. Public inventory queries remain detached from the cached metadata. Evidence updates and read-only queries reuse the compiled notification policy. Source changes rebuild it; settings reload creates a new runtime. Unchanged reconciliation retains the existing compiled policy and its attention clocks.

[ADR 0010](adr/0010-large-inventory-updates.md) records the ordered runtime and compact-transport decision. Catalog metadata has an in-memory revision. The optional `compact: true` dashboard subscription uses schema version 2: its first available event includes the complete catalog, areas and floors with `inventory_changed: true` and a `catalog_revision`; subsequent events at that revision omit those static fields and set `inventory_changed: false`. Dynamic problem, readiness, coverage, history and control fields remain complete replacements. A catalog change, reconnection, runtime replacement or recovery from unavailability sends a full baseline. Clients reject a delta without a matching available baseline. Legacy subscriptions remain full schema-version-1 snapshots. This reduces repeated transfer; the initial catalog remains a full snapshot. House/coverage source tables render at most 50 rows per page and search the complete received inventory by name, identity, kind or monitoring label. Search and page survive evidence updates; a location change resets the source selection. Cached client lookup/location models are replaced with the catalog baseline.

Initial settings: settle 120 seconds, rejoin grace 60 seconds, startup grace 120 seconds, longest startup wait for integrations 600 seconds, coalescing count 3 and window 60 seconds, notification batch 30 seconds, clear hold 120 seconds, unknown hold 900 seconds. Availability failures have zero raise hold; setup retry has a 120-second warning period across unsuccessful setup attempts. SETUP_IN_PROGRESS does not reset the retry onset; leaving the retry cycle does. The panel edits these durations. Availability checks use no observation expiry because they read HA's current state; physical freshness is explicitly unsupported. The reconciliation timer is adapter plumbing, not a physical heartbeat. Apply startup grace when Home Assistant starts; a Homeostatic integration reload while HA is running, including a panel save, skips it. Preserve the configured startup duration for the next full HA start.

A sweep reads all enrolled sources into one observation batch; other refreshes observe only the sources whose events arrived. It registers new or changed nodes together through `Engine.register_many` before ingesting observations, preserving existing check state and validating the final topology. Initial setup likewise registers its graph in one batch; unchanged reconciliation does not register nodes again. It keeps missing selected nodes as unknown. Explicit unenrollment removes their nodes; a removal notice is not presented as physical recovery.

Ordinary available-value changes do not trigger a new availability observation or snapshot write. Changes between available, unavailable, unknown, missing, and restored evidence do. A vacuum activity change is observed even when that availability signature stays the same. The periodic sweep still refreshes the available HA evidence.

## Attention and persistence

Notifications default to off. The integration emits `homeostatic_notification` events for policy deliveries. Selected `phone:<HA device registry id>` and `notify:<HA entity registry id>` channels also request delivery through Home Assistant notification actions. Other channel ids remain consumer-owned; the optional automation blueprint continues to use the event. Persistent notifications are reserved for failures of Homeostatic itself. Delivery means requested, never received or read.

Named monitoring policies own their notification entries. Current notification definitions compile those entries into the library's recipients, schedules and ordered rules. Compilation preserves independent notification-entry identities, explicit dashboard-only choices and restart state. Saved raw attention-policy data is not an alternate configuration path. The public attention preview accepts an explicit simulation policy without saving it.

Delivery tests are available within saved reusable methods. The administrator-only test action resolves and validates the saved targets before requesting its fixed message. It does not create an episode, change attention clocks or enable notifications. Test results describe requests, never receipt. Built-in Companion delivery supports an explicit Acknowledge action for eligible individual issues, device messages and collected messages, bound to the exact issues shown in that request.

On activation, the integration asks the library to restart attention for current open episodes after reconciling observations. Episode history and age matches remain unchanged. Escalation starts at activation; reminders start with the first delivery request. Reusable notifications enter their saved collection window after eligibility. Supported inline Custom findings retain their existing device and activation-summary presentation. Urgent and delayed recipients can receive messages at different times. Digest-only problems wait for their named report, and record-only problems produce no event. An empty activation produces no problem notification. Ordinary reload restores clocks without replaying openings. Reusable notification edits restart only changed routes; name-only edits retain clocks and delivered state. Built-in phone routes process withdrawal requests even when outgoing requests are off, using the previous tag; optional event consumers receive the same withdrawal event.

After attention authorization, public health-tree `DeliveryCollections` collects reusable notification requests by saved notification identity, recipient, resolved destination and compatible accepted instructions. A common device, integration or cause is unnecessary. Different saved identities stay separate even with identical names and settings. Inline Custom assignments retain their existing compatible device presentation. Independent issues retain their evidence, clocks and controls. Public immutable membership records supply exact issue and route identities; persistence snapshots remain opaque.

The first eligible request starts a fixed collection window. Later requests never extend its deadline. `timing.collection_delay_seconds` is a required whole number at least zero for named immediate, acknowledgment and daily-hours notifications; zero releases without waiting. These routes override ordinary policy batching with zero to avoid stacked waits. Startup holds precede the collection window. Overnight daily-hours requests enter only when hours open; ended issues stay out. A deadline after hours close waits for the next allowed opening without a second collection delay. Scheduled reports bypass collection entirely. Empty windows send nothing. Newly eligible requests after closure start another window; silent updates retain their original message membership.

The library persists pending membership, deadlines, accepted instructions and resolved targets together with delivery state. Edits to saved definitions do not retarget pending requests or restart their delay. Removed assignments and ineligible issues leave pending membership. Absorption preserves pending and presented attention without replaying an opening; new assignments remain independently eligible. Each outbound collection lists its exact issue IDs, and acknowledgment applies only to IDs shown in that request. Partial recovery updates the remaining members without clearing them. Transport replay retains the durable delivery ID and accepted channels.

A supported inline Custom device message keeps its tag across new findings, partial recovery and restart. Partial recovery silently replaces it with the remaining authorized findings; only the last member ending withdraws it. Monitoring removal is distinct from observed recovery. A changed device association moves the affected finding to its current notification subject on the next authorized message update, without claiming recovery or withdrawing other members. Registry changes alone do not create attention. A new qualifying issue can request attention even if earlier members were acknowledged. Presence is resolved for new requests before grouping. Silent updates and withdrawal retain prior destinations without adding unseen findings to destinations that did not receive them. Persist group membership with durable delivery state and preserve outbox delivery IDs across replay.

Events distinguish open, activate, update, remind, escalate, resolve, summary and digest actions. Identical reminders are still emitted; silent identical replacements are deduplicated. Scheduled digests retain their report grouping and route identity. Supported inline Custom startup and activation findings for devices and standalone entities use their continuing subject messages; summaries for other source kinds retain their existing per-recipient and route contract. A summary resolution silently refreshes the remaining membership, and its last resolution clears its tag. A later individual reminder or escalation can move an issue out of a non-device summary. See [events.md](events.md).

`policy` returns public library explanations for current episodes. `preview_policy` validates an unsaved policy and restores an isolated copy through the opaque public snapshot API, then simulates activation at the current time. It returns initial delivery requests, evaluated rules, recipients, pending times and the next deadline, without saving or sending, including while notifications are off. It is an activation preview, not a forecast of future evidence. The panel validates each policy draft when Save policy is selected. The read-only preview API does not impose a separate UI step. Physical receipt remains outside the request contract.

A Home Assistant start holds notification requests until watched integrations finish loading, for at least startup_grace and at most startup_quiet_max. Reusable collection windows begin when that startup hold ends. Supported inline Custom findings retain their existing device or per-route startup presentation. An overdue reminder updates its subject's existing message once; restart does not replay openings or accumulated reminders. Scheduled reports keep their report contract. Reloading the integration while HA runs has no hold. See [events.md](events.md#restart-and-activation).

Persist engine state, policy state, episode presentation, authorized delivery-group membership, last requested messages, delivery attempts, and a delivery outbox in a versioned HA Store. Restore policy before feeding engine restore events. Reconcile current observations before releasing pending openings; cancel an unsent opening when its episode has resolved. Save before firing events and save the cleared outbox afterwards. A crash between emission and acknowledgement can replay the same delivery id: delivery is at least once. The built-in sender saves one attempt per delivery id and channel before calling the HA service, so a plain message is not repeated after replay; this can lose a message if the process stops after the attempt is saved and before the service call. Phone requests use a stable tag for replacement. At the built-in phone sender and Companion blueprint boundaries, tags exceeding 64 UTF-8 bytes become the lowercase SHA-256 hexadecimal digest of the complete tag. Shorter tags remain unchanged. Opening, updating and clearing use the same transformation, preserving recipient separation and Apple APNs collapse-id limits. Public event tags and persisted delivery identity remain unchanged. HA mobile-app services can log provider errors without raising them; absence of a caught service error does not prove provider acceptance. Event consumers must replace by tag or deduplicate by delivery id. Event publication and a successful service call are not acknowledgements of receipt.

Use atomic Store writes and read-back verification because Store can log a write failure without raising. Verification compares the stored file with the bytes the Store serializer produces for the same envelope, and parses and compares the content only when those bytes differ, so a serializer change cannot by itself make monitoring unavailable. Construct the snapshot under the runtime lock and keep it unchanged until verification finishes. Configure Store to serialize in the executor; verification also runs in the executor so large snapshots do not block the HA event loop. A refresh that queued no notification request and changed no episode, operator control or setting defers its save to a Home Assistant timer of at most 15 seconds and later such refreshes inside that window add no save; a request, an episode or control change, a settings save or shutdown saves immediately and verified, which also flushes a pending save ([ADR 0096](adr/0096-coalesce-evidence-saves-and-verify-bytes.md)). The snapshot persists durable facts: issue identities and history, operator controls, the delivery ledger, enrollment, monitoring identities and scopes, and timing progress. Route signatures persist as digests of their canonical JSON. One evidence map holds the latest observation of every source for the detail views and persists, as the `evidence` section, only the last known failure and whether history is complete; a failure that continues with the same reason keeps its first report, a source with no known failure and complete history is not persisted, snapshots with the earlier `check_evidence` and `integration_evidence` sections still load, and the first refresh after a restart rebuilds the current observation of every source. A save whose serialized bytes equal the last verified write performs no write; health-tree 0.9.0 keeps its engine and policy snapshots free of volatile observation state so that an unchanged refresh produces equal bytes ([ADR 0097](adr/0097-shrink-the-snapshot-and-save-durable-changes.md)). A settings save whose write or verification fails answers the caller with an error, marks monitoring unavailable and reloads the integration from the last verified store while the config entry keeps its previous options; there is no in-process rollback ([ADR 0100](adr/0100-a-failed-settings-save-reloads-from-the-store.md)). Evidence arriving during persistence remains queued for the next refresh. Invalid snapshots remain visible failures and must not silently discard history. Native invalid-JSON handling remains with HA and its storage-corruption Repair. Unsupported development envelopes fail visibly; the current envelope retains issue identities and delivery records across reloads.

The storage envelope is version 3 and requires validated `monitoring_identities` bindings and `monitoring_scopes`, which records the previously evaluated exclusions for each policy. Device bindings use the policy, canonical source and detector settings without exclusions as a stable lookup key. A version-2 envelope seeds its actual legacy check IDs from the saved policies before restoring the opaque engine snapshot. Version 3 never treats missing or invalid continuity metadata as an old installation. Current policy configuration remains authoritative; the stored scope is used only to distinguish a saved exclusion edit from registry changes. Preview computes the same proposed identities without updating the bindings or scope records. Removing the integration cleans up owned delivery requests from either supported envelope version. This storage change requires paired state and component rollback for any subsequent installation.

Unload and shutdown cancel all callbacks, drain captured observations, and attempt a final save. A failed final save leaves the last durable snapshot and creates a visible Homeostatic storage error; cleanup still completes so there is no stopped runtime registered as a failed unload. A platform refusal to unload keeps monitoring running. Work already saving cannot create a new timer after shutdown starts.

Phone destination choices group a Companion phone route and its mobile-app notify entity by their shared HA device registry identity, never by display name. Each device appears once per person. Existing selected route ids remain unchanged on viewing; a selected notify-entity route remains selected and usable. A new choice prefers the Companion phone route. Clearing a phone removes all selected aliases for that device in the draft; selecting it again chooses one route. Distinct device registrations remain separate even when their names match. Other notify entities remain independent destinations. These presentation changes do not edit HA registrations or send messages.

History in Monitoring explains each related open or retained ended problem with its source name, recorded finding, outcome, opening time, and (for ended problems) observed resolution time and recorded duration. Entries sort newest first by opening or observed resolution time. The read-only `resolved_history` action and additive `inventory.resolved_history` field return `{started_at, retention, episodes}`. `retention` contains `max_episodes: 100` and `max_age_days: 30`. Entries are newest resolution first. The adapter keeps only the latest 100 terminal episodes whose resolution was observed less than 30 days ago; expiry is applied to queries immediately and to persistence at reconciliation. This is bounded terminal history, not a full transition, configuration, operator-action or delivery journal.

Each entry contains `episode` (the public serialized library Episode, retaining its stable id, original opening time, findings and display labels), `resolved_at` (UTC ISO), `resolution` (`cleared`, `removed`, `absorbed` or `split`), `absorbed_into` (episode id or null), `split_into` (successor IDs, empty for other outcomes), and `source` (a display snapshot or null if the source is unavailable). The source records `node_id`, `name` and `kind`, plus known `owner_id`, `monitoring_source` and integration/device attributes for historical association. Runtime removal captures the previous source before replacing the inventory. A resolved child therefore remains discoverable from its recorded parent after rename, registry removal or reload. Existing entries without ownership metadata remain valid and retain limited association; current topology is not used to invent their historical membership. Episode findings/status describe the last episode evidence, not a current health claim. Source display text can fall back to the episode's labels when no current source exists. A rename or later fault does not rewrite an earlier history entry.

Only a library `EpisodeResolved` event creates an entry. Unknown evidence, shelving, maintenance and notification disablement are not resolutions. `cleared` records the library's recovery decision; `removed` records the end of monitoring, not recovery; `absorbed` links to the absorbing episode, which may remain open or later fall outside retention; `split` links to continuing independent issues without claiming recovery. Resolution time is when the adapter handles the event. After downtime it does not claim when the physical problem ended. A problem that clears before any notification was requested still appears in history.

History is saved in the same atomic, verified envelope as engine/policy state and the outbox. Restore loads it before handling engine restore events. Duplicate episode ids are not appended on replay. Malformed stored history fails setup visibly and leaves the stored envelope intact. Older envelopes with no history field start an empty history at their first running evaluation; `started_at` identifies when collection began, without reconstructing earlier resolutions. Read responses are detached, produce no notifications and do not advance the engine or policy. Removing the Homeostatic entry deletes history with the rest of its owned storage. Existing `inventory.episodes` remains the open-episode list.

## Operator controls

`homeostatic.shelve` holds new notifications for one current episode until an explicit time. It applies to every recipient, including urgent notifications, reminders and escalations; it does not acknowledge or resolve the problem. Existing messages remain visible, and the library may update them silently or clear them on resolution. Pending library deliveries remain subject to their other holds. A shelf can be extended or ended early with the explicit cancel-control action. Situation episodes can be explicitly shelved by their own episode id.

`homeostatic.start_maintenance` creates an engine quiet window for one equipment capability (`entity`, `integration`, or `external`), optionally including its dependency-graph dependents. No global scope is exposed. `preview_maintenance` returns the current scope, already-open episode ids without changing anything. The start action recomputes and returns the scope applied. Dependents follow the graph as it changes during the window. Situations have no edges to or from equipment; both graph validation and maintenance scope validation enforce their separation. Situation roots and any scope containing a situation are rejected.

Maintenance prevents new episodes in scope. It keeps observations, readiness, existing episodes and their notifications active. A continuing fault opens after expiry subject to the library's normal rules; a fault that recovers inside the window produces no later episode. Shelving an existing episode is a separate explicit action.

Maintenance creation is available only through the published Home Assistant actions. The panel omits its entry points, duration and scope form, preview and submission paths under [ADR 0087](adr/0087-remove-maintenance-creation-from-ui.md). Both mutations require HA administrator access when called with a user context; HA-owned automations without a user context follow HA's standard admin-service authorization. Both accept `until` as an ISO timestamp with a timezone, normalized to UTC, strictly in the future and at most seven days away. There is no default expiry. Optional `reason` is at most 500 characters. Actions serialize with observation processing, reconcile captured evidence first, and persist before returning success or publishing resulting notification requests. Requests already authorized in the durable outbox retain their replay identity; controls do not retract previously authorized events. A storage failure returns an error and makes monitoring unavailable until persistence recovers; an errored request may remain in memory or on disk, so inspect controls after recovery before retrying.

`operator_controls` and inventory list active requested controls with a generated id, target, start/expiry, actor user id (null for system context), reason and dependent-scope flag. This presentation is persisted separately from opaque library snapshots. Expired controls, shelves for resolved episodes and maintenance for removed nodes are removed. Deadline scheduling includes control expiry, even when no notification is due. Reload restores the library's holds and the adapter's control records together. These are current controls, not a permanent audit history. Early cancellation and acknowledgment use the actions defined above.

The dashboard offers shelving from an open episode. Its form requires an explicit local end date/time, converts it to zoned UTC, and allows an optional reason of at most 500 characters. It explains that the pause holds new notifications for every recipient, including urgent notifications, without resolving the problem or removing existing messages. The form saves directly after validating target and expiry. Read-only maintenance previews and scoped start actions remain available to API callers; the start service recomputes and returns the applied scope. Situations remain ineligible as maintenance roots.

Live updates preserve form values. A disconnected, unavailable or non-admin view cannot submit; a resolved shelf target or ended control cannot submit. Duplicate clicks while a request is pending cannot send duplicate actions. There is no automatic retry after an ambiguous action failure: the form asks the owner to inspect active controls after recovery. Successful actions show the returned saved control, expiry and reason. Active controls are readable on overview and in node/problem details; eligible problems offer Acknowledge issue, and current temporary controls offer Resume notifications or End maintenance. Controls and history use existing schema-version-1 fields and native service responses without adding another runtime update path.

## Automation-reported situations (ADR 0032)

A situation declares either an `entity` or a `report_timeout` integer from 60 to
86400 seconds, never both. The latter accepts the administrator action
`homeostatic.report_situation` with its configured `situation_id` and `state`
(`active`, `clear`, `unknown`). HA automations without a user context use the
normal administrator-service convention. Reports never create configuration.
Only one automation should own each id; calls are applied in serialized arrival
order using adapter UTC acceptance time. Retrying the same state retains the
episode and refreshes evidence; it is not a new occurrence.

The existing condition check uses report_timeout as its TTL. Reports map to
fail/pass/unknown; expiration never resolves an open episode. The normal
unknown_hold then governs stale attention. Ordinary reconciliation never renews
a report. Every setup/reload requires a fresh report: a restored open episode
retains its identity and receives unknown before current reports arrive.
The source is edgeless, excluded from readiness, and protected from equipment
maintenance, like an entity-bound situation.

Actions use the same serialized persistence-before-publication path as operator
controls. Storage failure returns an error, publishes no new delivery, and marks
monitoring unavailable; inspect state after recovery before retrying. No separate
report store, lifecycle or notification bypass is introduced. Reports do not
enable notifications, create recipients, or prove delivery. One-shot informational
events are outside this increment.

The supplied automation blueprint checks all declared evidence entities, reports
unknown for missing/unknown/unavailable/restored evidence, otherwise evaluates
native HA conditions and reports active or clear. It reevaluates on source
changes, HA start, each minute, and optional owner triggers. Configure timeout
longer than this cadence. Disabling/removing the reporter causes expiry, never
clear. Conditions run inside the action sequence so a false result reports clear
rather than skipping the automation. Startup races retry on the next minute.
Owners must list every entity needed as evidence and use one reporter per id.
Conditions describe continuing states; trigger-specific event predicates require
an owner-maintained state source instead. HA owns timer/restart semantics.

Condition evaluation errors (such as nonnumeric temperature values) report unknown.
The blueprint checks both the positive condition and its explicit negation;
falling through an errored condition does not report clear.

on the next report; report text is limited to 2000 characters and names to 200.

Active registrations are capped at 1000 per installation; retired records do not use
that capacity. `manage_alert` explicitly retires/resumes an owner/key. Retirement
removes monitoring (not recovery) and blocks refresh from re-enrolling it until
resumed. Disabling an automation alone expires evidence to unknown. When HA removes
the owning automation from its entity registry, reconciliation deletes its declaration
and ends any open issue as removed from monitoring. Optional administrator
`adopt_situation_id` transfers an existing report-only declaration to automation
ownership while preserving its node and episode; entity-bound declarations must
remain entity-bound. The old declaration is retained but shadowed, including while
retired. The old report_situation action rejects transferred identities.

Built-in phone delivery adds Acknowledge to active individual issues, device messages and collected messages. Each opaque callback reference freezes the exact represented episode IDs and is private to the delivery, recipient and phone. It is persisted before transport. A later member or occurrence cannot be acknowledged through that reference. One integration listener accepts only remote events with HA-authenticated, active user context matching the current phone owner and a still-permitted recipient route. Payload actor/device values grant no permission. Intended recipients need no admin role for this narrowly scoped callback; administrator services retain their authorization. References expire after 30 days, are capped at 2000 with oldest eviction, and survive restart. Duplicate acknowledgments are idempotent. Callbacks while delivery is disabled or after a route is removed do nothing.

Phone dismissal and clear requests are not acknowledgment or receipt. Main taps
retain ADR 0033 behavior. Non-device summaries, digests and resolution notices have no acknowledgment button.
Legacy event-only consumers retain their existing behavior; authenticated phone
actions are provided by the built-in person/phone sender. Evidence alone resolves
conditions. Tests use isolated HA and mocked phone transports.

### Dashboard connection guidance during updates

A subscription rejected because the backend does not accept the dashboard's
`paged` option is a version mismatch, not a health finding or proof of slow startup.
Show plain-language guidance to let any HA restart finish and refresh the page,
then check matching installed versions if it persists. Keep unrelated connection
errors distinguishable. An unavailable runtime without a reported error explains
that startup updates will appear automatically when monitoring becomes ready.
Neither message changes monitoring, retries mutations, or hides a stored error.
